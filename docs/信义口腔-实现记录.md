# 实现说明

本系统依据课堂板书与业务规约实现，案例统一为**信义口腔**。

## 保留的核心设定
- 13 个系统用例、26 张数据表、边界-控制-实体三分法、«moment-interval»/«thing»/«description» 构造型。
- 愿景：引流、提效、经营核算；目标取舍中"取消率/爽约率受患者主观因素影响大，不作为目标"。
- 患者侧入口为小程序；内部员工用浏览器管理端；两端共用一套服务端与数据库。
- 费用口径：收入＝收费单实收；成本＝项目成本标准×实际项目；期间费用＝房租＋水电＋耗材采购＋其他；利润＝毛利－期间费用。
- 价目数据：`treatment_item` 64 项按 2026 年公开参考区间取常见值（洁牙 98/198/398、补牙 260/320/600、根管 650/1000/1600、拔牙 180/650/1200、全瓷冠 1800/3500、瓷贴面 2800、种植 3500/3980/4800/12000、半口 18000、全口 38000、正畸 9800~42000 元）。`item_cost` 按类别设置差异化的材料/人工/分摊比例，种植与正畸材料占比高，洁牙与外科人工占比高，避免所有项目同比例导致毛利失真。均为 mock 数据，不代表任何机构实际报价。
- 绩效按（门店，月份，牙医）归集接诊人次、项目收入、套餐售卡数。

## 按板书/规约校正或简化的点
1. "降低预约取消率"是通用设想；本案例不把取消率作为考核目标，系统仅统计预约状态与号源释放，不设取消率 KPI。
2. 板书演示为 TypeScript 模块化单体 + PostgreSQL + 独立 worker；本系统用 TypeScript/Node.js 模块化单体 + PostgreSQL + worker，技术口径一致。
3. 结算为确定性实现（收款方式＋自动计价＋套餐抵扣），不引入真实支付网关；收费单按就诊记录生成，重复结算被状态机拒绝。退款按板书要求补齐：以原收费单实收为上限、幂等键防重复、需负责人或院长审批，详见 `refund_request` 表与 `/api/refund/*`。
4. 发票一期为人工核验登记，未在本系统开放接口开票。
5. 微信小程序受开发环境与 AppID 限制，本地以 H5 模拟端呈现，接口与用例保持一致。

## 按用户要求的前端/后端拆分
用户明确要求"前端后端要分开"，因此从单一角色切换页重构为按端/模块分离的多个应用（登录体系见下一节）：

- **患者端（客户端/小程序）**：`patient.html` + `/api/patient/*`。可预约、取消预约、查看复诊提醒并一键发起复诊，含套餐卡与治疗计划。
- **牙医工作站**：`dentist.html` + `/api/dentist/*`。写病历、开处方、制定治疗计划。
- **管理网站**：`admin.html`。其中**费用模块**（`/api/finance/*`）与**绩效模块**（`/api/performance/*`）作为两个独立模块：
  - 费用模块逐项回答"每个项目花了多少钱、收费多少、房租水电、购买医疗产品、利润"：项目收支字典给出收费价与材料/人工/分摊成本及毛利；期间费用归集房租水电等；采购单覆盖医疗产品采购；利润按收入−项目成本−期间费用核算。
  - 绩效模块按连锁口径给出医生绩效排名与门店对比。
  - 前台/院长/库管的排班、套餐、库存、报到结算、随访走 `/api/admin/*`；按登录岗位过滤可见菜单。
- **数据库**：`db.html` + `/api/db/*`。展示 34 张表的字段、DDL、映射说明与模拟数据。

后端职责边界：`domain.ts` 只放跨端共用的领域规则（预约/号源、结算、套餐、采购、利润、绩效、复诊 worker）；各 `routes/*.ts` 负责本端的接口编排；`server.ts` 只做挂载。

## 登录、角色与借调（按用户后续要求补充）

用户进一步要求"登录分客户端和专业端、不同职责进不同页面、预留注册、院长可兼医生、医生临时借调"。落实如下（UI 里不出现"专业端"字样，统称工作人员登录/工作台）：

1. **三个入口，登录后分岗**：门户只有「客户端（患者）/ 工作人员登录 / 数据库」。工作人员统一从 `/staff.html` 登录，按 `active_role` 进入医生/院长/分院负责人/前台/库管工作台；管理网站按岗位过滤左侧菜单（`admin.js` 的 `GROUPS.roles`）。UI 统一称「工作人员」，不出现「专业端」；本轮只增加分院负责人，不扩出其他岗位。
2. **分院负责人**：`store_manager` 表记录门店—负责人。总院由院长管理，观山湖/世纪城/思南门诊分别设置负责人；负责人可看经营驾驶舱、费用、绩效、员工与借调，体现分院"看财务、管其他人"。
3. **注册 + 短信 + 审批**：注册页不填工号，系统自动生成工号，手机号即登录账号；注册填「密码 + 确认密码」两次，前后端双重校验一致才受理；`/api/auth/staff/register` 提交后账号状态为「待审批」，并调用模拟短信适配器向该手机号发送"注册已提交"短信，留痕于 `sms_message`（真实项目对接短信网关）。**负责人或院长任一方通过即开通**，两方均不通过才最终拒绝；账号状态确定后再发一条结果短信。每次审批写入 `approval_record`，管理端显示审批意见。密码用 SHA-256 存 `password_hash`（mock 环境，生产应加盐与更强哈希）。
4. **修改密码**：`/api/auth/staff/change-password` 校验原密码正确 + 两次新密码一致 + 新密码不同于原密码，更新 `person.password_hash`（SHA-256），旧密码立即失效；同时写 `sms_message` 通知绑定手机号。管理端与医生工作站顶部「修改密码」按钮复用 `core.js` 的 `bindChangePassword()` 弹窗。
5. **一人多角色**：`staff_role` 表存"人员—角色"多对多；院长王建国同时是院长与牙医，`staff_session.active_role` 记住当前身份，右上角一键切换；医生工作台固定为登录医生本人，不能替他人开方。
6. **患者登录**：手机号 + 模拟验证码（`MOCK_CODE=1234`）登录，`patient_session` 保存会话；登录后各查询固定用登录手机号，只看本人数据。
7. **临时借调**：`doctor_transfer` 表记录"牙医—原店—目标店—起止日期—审批人"。负责人或院长任一方通过后：释放原门店该时段的**未锁定**排班，在目标门店生成排班；原门店**已有预约**（locked>0）的时段保留以履约，不重复排班。两方均不通过才最终驳回。结束借调清理目标门店未锁定排班。目标店接诊按 `visit_record.store_id` 计入目标店绩效。
8. **表数量由 26 增至 34**：新增 `staff_role`、`patient_session`、`staff_session`、`doctor_transfer`、`store_manager`、`approval_record`、`sms_message`、`refund_request` 八张支撑表，业务 26 张表结构与映射不变。

## 验证方式
- 本地：`DB_MODE=memory npm run dev` → 打开 `http://localhost:3000` 从入口进入。
- 端到端闭环（已通过）：患者验证码登录 → 预约 → 取消释放号源 → 复诊一键预约；员工注册（免填工号）→ 注册短信留痕 → 待审批登录被拒 → 负责人或院长任一方开通 → 结果短信 → 登录成功；院长⇄医生身份切换；借调申请 → 任一方审批（释放原店12班/目标店生成12班）→ 号源转移 → 结束清理；原有预约→签到→病历处方→结算→利润→绩效全链路回归通过；数据库表清单 34 张；退款申请→审批→冲减收入闭环、越权访问被拒等已验证。
- 服务器：Portainer 部署后进入 `http://IP:3000`，工作人员先登录再进各自工作台，共用同一套 PostgreSQL 数据。
