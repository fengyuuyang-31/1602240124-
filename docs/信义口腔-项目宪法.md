# 信义口腔连锁管理系统 · 项目宪法

> 对应课堂板书 `speckit.constitution` 产出物。本文件定义不可协商的原则，spec / plan / data-model / tasks 各阶段均须服从。

**版本**：1.0
**日期**：2026-11-24
**状态**：已生效

---

## 第一条 案例与数据

1. 案例统一为 **信义口腔（连锁口腔门诊部）**，所有文档、页面、数据库 seed 中不得出现其他医院名称，不使用“贵州”前缀。
2. **全部数据为模拟数据**。不得录入真实患者姓名、身份证号、手机号、病历。演示手机号统一使用 `1380001xxxx` 号段。
3. 价格采用 2026 年公开参考区间的常见值，仅在系统内作演示，必须标注“模拟数据”。

## 第二条 架构不可退化

1. **前端与后端必须真正分离**：后端为独立 Express 服务并暴露 HTTP API，前端为独立静态页面，通过 API 交互。禁止把业务逻辑写回单个 HTML 页面。
2. 按端拆分页面：患者手机端、工作人员登录、牙医工作站、管理网站、数据库查看页各有独立入口。
3. 业务规则集中在后端 `src/domain.ts`，路由只负责参数校验、鉴权与转发。前端不得承担唯一的规则判定。

## 第三条 身份与权限

1. 患者与工作人员使用**两套独立的令牌与接口**（`x-patient-token` / `x-session-token`），不得混用。
2. 所有个人数据接口必须由令牌反查身份，**忽略请求参数中自报的手机号、员工 ID、医生 ID**。
3. 采用 RBAC：院长、分院负责人、前台、库管员、护士、牙医各司其职；服务端逐接口校验，不允许“前端隐藏菜单”代替鉴权。
4. 一人多角色通过 `person + staff_role + staff_session.active_role` 实现。院长兼牙医必须可切换身份。

## 第四条 审批与业务硬规则

1. 注册、借调、退款均需审批。**分院负责人或院长任一方通过即生效**，两方均不通过才最终驳回；院长的审批权不得被剥夺。
2. 医生只能被预约其**可约时段**；同一家连锁内跨门店排班不得冲突；同一患者同日仅一条有效预约。
3. 借调必须保留原门店已有预约的班，释放的只是空闲班；目标门店按椅位找真正空闲时段，结束借调只清理本单生成且未锁定的排班。
4. 支付与退款必须幂等：退款用唯一键防重复提交，累计退款不得超过原收费单金额，审批通过后冲减账单。
5. 利润口径唯一：**收入 − 项目成本 − 期间费用**；项目成本按 `effective_date` 取最新版本，不得重复累加。

## 第五条 部署与可运行性

1. 正式环境使用 **PostgreSQL**；内存库仅用于本机演示。
2. 交付物必须能以 `docker compose up -d --build` 在 **Linux + Docker** 服务器上一键启动，含 app / worker / postgres 三个容器。
3. app 与 worker 并发启动时，数据库初始化必须加事务级锁，防止重复灌种子。
4. 复诊提醒由**独立 worker** 执行，应用进程不得重复执行。

## 第六条 交付与表达

1. 界面视觉统一为**淡蓝色系**，术语统一（不出现“专业端”等不一致叫法）。
2. 首页徽标固定为两个独立框：`信义口腔` / `模拟数据`。
3. 文档中不保留“大作业 · A–D 工作流落地”等过程性标语；规格文档只描述最终系统。

---

## 宪法对后续阶段的约束

- `spec.md` 中的每条需求不得与上述条款冲突。
- `plan.md` 的技术选型必须能支撑第三条、第四条的鉴权与规则要求。
- `data-model.md` 必须能落地第四条的幂等、审批、成本版本、跨店绩效。
- `tasks.md` 每一项完成后须能回溯到本宪法对应条款。
